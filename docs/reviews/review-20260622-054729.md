## Executive summary

1. **An out-of-range handle aliases onto a live slot and returns another handle's value — in BOTH radix trees** (`src/handle_table.rs:674`, `src/membership_index.rs:152`). The depth-0 capacity guard is gated on `self.depth > 0`, so at depth 0 it is skipped and `find_leaf` returns `handle % ENTRIES_PER_LEAF` for *any* handle. Verified end-to-end: with 100 handles allocated (tree at depth 0), `db.read(Handle::from(516))` returns `Ok("value-5")` — handle 6's value — instead of `InvalidHandle`. `Handle: From<u64>` is public, so callers can fabricate the handle; `read`/`tag`/`client_byte`/`update`/`delete_tagged` all reach it. A confidentiality/correctness break, masked by a comment that justifies skipping the guard because "`handle % ENTRIES_PER_LEAF` is already total." (BUG)
2. **A `SpillwayFull` during eviction silently discards a dirty page, violating commit atomicity** (`src/page_cache.rs:996-1011`). In `maybe_evict` Phase B the LRU-tail dirty victim is removed from the cache *before* `spw.spill(...)?` is attempted; on `SpillwayFull` the `?` propagates and the page's bytes are dropped. `SpillwayFull` is *operational* (non-fatal, doesn't poison) and the public docs say operational errors leave the handle usable — so a caller may continue and commit, at which point the committed superblock points at a handle-table page that silently reverted to stale committed content. (BUG)
3. **The single-page freemap silently stops reclaiming space past ~512 MB** (`src/freemap.rs:72-115`). `next_page_id` is an unbounded monotonic allocator, but the freemap tracks only ids `0..65344`; `mark_free` *no-ops* any id beyond that and `allocate_first` never scans past it. Past 65,344 pages every freed page leaks forever with no error — the COW steady-state (bounded handle-table/membership page count, and the I118 `free_subtree` reclamation just landed) silently degrades to monotonic growth. (DESIGN)
4. **The overflow-chain walk trusts page type, unlike the heavily-hardened data page** (`src/overflow.rs:152-250`). `Overflow::read`/`delete` never check `buf[0] == PageType::Overflow`; a checksum-valid page of the wrong type reached via a stale/buggy handle entry is parsed as overflow metadata. `data_page.rs` defends exactly this (a whole `corruption_tests` module); overflow has no equivalent guard — an asymmetry in a codebase that treats data-page type validation as load-bearing. (DESIGN)
5. **A reachable integer-overflow panic in `Chisel::open` — found and fixed during this review (PR #66)** (`src/transaction.rs:494`). `FileSizeMismatch` computed `sb.total_pages * PAGE_SIZE`; `total_pages` is unbounded by `deserialize`, so a crafted superblock with `total_pages > u64::MAX/8192` panics in debug (how CI runs) / wraps in release. Fixed with `saturating_mul` (the I47 pass fixed the `stats()` siblings but missed this site) + a `total_pages = u64::MAX` regression test. (BUG — resolved)

## Findings by category

### Correctness

- **BUG** — `src/handle_table.rs:674 (find_leaf depth-0 path, lines 678-681)`
  - **What:** At depth 0, the capacity guard `if self.depth > 0 && cap != u64::MAX && handle >= cap` is skipped entirely, so `find_leaf` returns `Ok(Some((page_id, handle % ENTRIES_PER_LEAF)))` for ANY handle. An out-of-range handle aliases onto an occupied slot. Verified end-to-end against the public API: with 100 handles allocated (tree at depth 0), `db.read(Handle::from(516))` returns Ok("value-5") — the value of handle 6 (516 % 510 = 6 % 510 = 6's slot) — instead of `InvalidHandle(516)`. This reaches `read`, `tag`, `client_byte`, `update`, and `delete_tagged` via `lookup_live`. `Handle: From<u64>` is public, so callers can fabricate out-of-range handles.
  - **Why:** Violates the documented contract that an unknown handle surfaces as `InvalidHandle` (see I26 / I6 history and the lookup_live doc at transaction.rs:1611). A fabricated or mistaken handle silently returns another handle's value (a confidentiality/correctness break), and `update`/`delete_tagged` on such a handle would mutate the aliased entry. Notably `delete` (handle_table.rs:289) and `RadixU64::delete` already guard `handle >= capacity()` at depth 0 — only the read/find_leaf path was left unguarded, an inconsistency that signals the omission.
  - **Fix:** Apply the capacity guard unconditionally (drop the `self.depth > 0` qualifier), e.g. `if cap != u64::MAX && handle >= cap { return Ok(None); }` placed before the depth-0 early return. At depth 0 `capacity() == ENTRIES_PER_LEAF`, so this correctly rejects handle >= 510 instead of wrapping via modulo.

- **BUG** — `src/membership_index.rs:152 (RadixU64::find_leaf depth-0 path, lines 155-157)`
  - **What:** Identical depth-0 hole to the handle table: `if self.depth > 0 && cap != u64::MAX && key >= cap` skips the guard at depth 0, so `find_leaf` returns `(root, key % SLOTS_PER_PAGE)` for any key. A depth-0 inner tree (tag with <1021 members) queried with handle >= 1021 aliases onto an in-range slot. `MembershipIndex::contains(tag, 2000)` would return a false `true` when handle (2000 % 1021) is a member.
  - **Why:** Same class as the handle-table bug. Production impact is lower because `contains` is `#[allow(dead_code)]` and inner-tree lookups in the live path always use the exact inserted handle, but it is a latent correctness gap in a `pub(crate)` API and will bite any future caller (or index-consistency check) that looks up an arbitrary handle.
  - **Fix:** Same fix as the handle table: make the `key >= capacity()` guard apply at depth 0 too (remove the `self.depth > 0` qualifier), since at depth 0 capacity == SLOTS_PER_PAGE.

- **BUG** — `src/page_cache.rs:996-1011 (interacts with src/spillway.rs:164-188 spill / SpillwayFull)`
  - **What:** In maybe_evict Phase B, the LRU-tail dirty victim is removed from self.entries and self.lru and run through untrack_dirty (lines 996-1005) BEFORE spw.spill(victim_id, &entry.buf)? is attempted (line 1011). When spill returns ChiselError::SpillwayFull, the `?` propagates and `entry` is dropped at scope exit. The victim's dirty (uncommitted) page bytes are silently discarded — never written to the main file, never spilled. A subsequent get(victim_id) misses and load_page silently re-reads the last-committed bytes from the main file (page_cache.rs:200-204).
  - **Why:** SpillwayFull is classified operational/non-fatal (error.rs:456, is_fatal() == false), and lib.rs:268 documents the contract explicitly: "Operational errors leave the handle usable: fix the condition (or rollback) and continue." So a caller may continue the transaction and commit after a SpillwayFull. If the dropped victim was a page modified earlier in this transaction and still referenced by current_roots, its in-transaction modification is lost with no error: flush() writes only pages still in the cache, and the committed superblock then points at a handle table whose page silently reverted to stale committed content. That is a silent durability/atomicity violation, not just lost work. The CacheFull-disabled branch (973-977) is safe because it errors before removing any victim; only the SpillwayFull path drops a page.
  - **Fix:** Do not remove the victim from entries/lru until the spill succeeds, or re-insert it (and re-track dirty / re-add to LRU) on the SpillwayFull error before returning, so the page remains in the cache. Then a continue-after-error sees the still-dirty page and a rollback discards it cleanly — neither path loses committed-but-uncommitted modifications. Add a test driving SpillwayFull through maybe_evict and asserting an earlier-modified page survives a later commit (or that the manager refuses to commit).

- **DESIGN** — `src/freemap.rs:72-115 (capacity/mark_free) + src/page_cache.rs:327-340 (new_page)`
  - **What:** next_page_id is an unbounded u64 monotonic allocator (new_page: self.next_page_id += 1, no ceiling). The freemap is a SINGLE page tracking only ids 0..PAGE_BODY_SIZE*8 == 65344 (freemap.rs:72). mark_free silently no-ops any id with byte_idx >= PAGE_BODY_SIZE (freemap.rs:112), is_free returns false for it (freemap.rs:99), and allocate_first never scans past PAGE_BODY_SIZE. There is NO FreeMapFull error and no guard anywhere that stops new_page/claim_page from handing out an id >= 65344. grep confirms no `>= capacity` / `FreeMapFull` check in the allocation path.
  - **Why:** Once a database grows past ~512 MB (65344 pages), every page freed at id >= 65344 is silently swallowed and leaks forever — allocate_first can never reclaim it, so the freed-page reclamation that the whole COW steady-state design depends on (handle-table / membership COW pages reaching a bounded page count) silently stops working with zero error surfaced. The freemap.rs header frames the single-page limit as 'a multi-page freemap is not yet implemented', i.e. a missing feature, but in practice it is an un-guarded silent-corruption cliff: data is still written correctly, but space reclamation degrades to monotonic growth past the wall.
  - **Fix:** Add an explicit bound: when next_page_id (or a freed id) reaches FreeMap::capacity(), return a typed FreeMapFull/capacity error from new_page/persist_freemap rather than silently leaking. At minimum, debug_assert the id is in range in mark_free instead of silently ignoring it, so the boundary is loud in tests.

### Error handling

- **DESIGN** — `src/page_cache.rs:442-456 (flush Phase 1b drain) + src/spillway.rs:235`
  - **What:** In the spillway drain loop, each page is rehydrated then spw.forget(page_id) is called (line 453) BEFORE self.io.write_page(page_id, &buf) (line 456). If write_page fails, the page's bytes have already been dropped from the spillway resident-set (forget removed the slot mapping) but were never written to the main file, so the only durable/in-memory copy of that dirty page is the local `buf`, which is then dropped on the `?` early-return.
  - **Why:** This is a strictly-ordered lose-the-data-on-error window analogous to Phase 1a, and like Phase 1a it is only safe because of the I1 poison model — but unlike Phase 1a there is no comment here flagging the forget-before-write hazard or the poison dependency. A future reader refactoring the drain (e.g. to make commit retryable, or to swallow a transient write error) would not see any warning that forget() has already destroyed the recovery copy.
  - **Fix:** Document the forget-before-write ordering hazard and its poison dependency inline (as Phase 1a does at lines 363-378), or reorder to write_page first and forget only after the write succeeds so a failed drain leaves the page recoverable from the spillway.

- **DESIGN** — `src/error.rs:289-304 (From<io::Error>), reached via src/page_cache.rs:1043 / src/spillway.rs:87-92`

- **Freemap ceiling intent.** Is the single-page freemap (`~512 MB`) a deliberate v1 scope cap or an oversight? The header frames a multi-page freemap as "not yet implemented" (a missing feature), but the allocation path has no guard, so it silently leaks rather than erroring. Are they a planned in-place defragger, or dead code to delete? The documented "caller must consume the mapping" contract has no integration coverage either way.
- **Spillway memory-mode growth.** For the in-memory backing, `next_slot_index` is monotonic-until-commit, so a long transaction that forgets/respills distinct pages grows RAM past `max_bytes` (charged against the live set only).
