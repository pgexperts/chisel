## Executive summary

1. **Superseded handle-table COW pages are never reclaimed — the file grows unboundedly, one 8 KB page
   per mutation.** `HandleTable::insert`/`delete` COW the whole root→leaf spine via `PageCache::new_page`
   (a pure monotonic allocator) but never report the superseded pages, and the transaction layer only
   ever feeds *data* and *overflow* frees into the freemap. An empirical probe confirmed **+1.00 page per
   `update()` and per `set_client_byte()`** (2000 ops → +2000 pages), forever. The `freemap.rs:14-17`
   comment actively claims the opposite ("their frees do feed the freemap on commit"). (BUG)

2. **The forward handle→tag map and the reverse tag→handles index can be committed out of sync.** In
   `allocate_inner` the handle-table root is advanced (`transaction.rs:1227`) *before* the membership-index
   insert (`:1236`), which can return the **non-fatal** `CacheFull`/`SpillwayFull`. Because those don't
   poison, a subsequent `commit()` — the documented recovery from `CacheFull` — durably persists a chunk
   whose `tag()` works but which `handles_with_tag()` omits. `delete_inner` has the mirror gap, where the
   surviving stale index entry later escalates to a fatal `CorruptPage`. (BUG)

3. **Corrupt-but-checksummed radix pages drive depth out of range, causing a library-reachable panic
   instead of a typed `CorruptPage`.** `membership_index.rs` derives an inner-tree `depth` from the top 6
   bits of an outer-leaf value (`unpack_inner`, `:442`) with no validation; `find_leaf`'s `span_at_level`
   /`capacity` then multiply `SLOTS_PER_PAGE` without overflow checks, and `read_slot` (`:24`) slices
   `buf[off..off+8]` unguarded → out-of-bounds panic. `recover_depth` (both this module and `handle_table.rs`)
   has neither a depth cap nor a cycle guard. This contradicts the engine's own established posture of
   converting such sites to `CorruptPage` (I14/I45/I49). (BUG — corrupt-input reachability)

4. **`ARCHITECTURE.md:397` documents the on-disk `Deleted` flag as `0x03`, but the code canonically writes
   `0x00`** (`handle_table.rs:101`), and the comment at `:103-107` calls `0x00 == Deleted` load-bearing
   (zeroed pages must read as all-tombstone). For a format that is "sacred within a major version," the
   spec being wrong about a flag byte is a real hazard. (BUG — docs vs format)

5. **Several durability-critical behaviors are verified only in-session.** The handle-0 / `next_handle`
   counter, the `delete_with_tag` relation drop, and the `delete_tagged` success path are each asserted
   without a close-and-reopen, so a mis-persist (e.g. a regressed `next_handle` that re-mints a live id,
   or a membership-index root that doesn't survive recovery) would pass the suite. (DESIGN)

## Findings by category

### Correctness

- **BUG — `src/transaction.rs:1218-1244` (and the leak surfaces through `src/handle_table.rs:445-560`):
  superseded handle-table COW spine pages are never reclaimed.**
  WHAT: Every `allocate`/`update`/`delete`/`set_client_byte`/`allocate_tagged` calls `HandleTable::insert`
  or `delete`, which COWs the root→leaf path with `cache.new_page()` (`page_cache.rs:327-329`, a monotonic
  `next_page_id += 1` that never consults the freemap) and returns only the new root. The old pages on the
  path are abandoned. The transaction layer's `txn_freed_pages` is fed only by data-slot and overflow frees
  (`transaction.rs:1465-1475` and the delete path) — never by handle-table pages — so `persist_freemap`
  never returns them to the bitmap.
  WHY: Unbounded file growth and write amplification on the hottest write path. A throwaway probe (2000
  same-handle `update()`s, then 2000 `set_client_byte()`s, in-memory) measured **exactly +1.00 page per
  operation** with constant logical data — the data slot is correctly reused, but one handle-table leaf
  page leaks every time. At depth *d* the cost is *d+1* pages per mutation. This is space-leak / write
  amplification, not data loss, but it is permanent and affects in-place-update and metadata-mutation
  workloads (exactly the access pattern the stable-handle design invites). It also makes the
  `freemap.rs:14-17` comment false (see Docs vs reality).
  FIX: Have `insert`/`delete` collect the page ids they supersede on the COW path (old root + each cloned
  interior/leaf, excluding freshly-allocated sparse children) and return them so the transaction layer can
  `txn_freed_pages.extend(...)` exactly as it does for overflow chains. The timing rules already proven safe
  for data pages (merge at commit, not reusable within the same txn — `transaction.rs:605-653`) apply
  unchanged. If reclamation is intentionally deferred, that must be documented and the freemap comment fixed.

- **BUG — `src/transaction.rs:1227` vs `:1236-1243` (allocate) and `:1588` vs `:1596-1605` (delete):
  forward/reverse tag maps can be committed out of sync.**
  WHAT: `allocate_inner` assigns `current_roots.handle_table_page = new_root` (entry carries `tag`) and
  *then* calls `membership_index.insert`, which allocates via `cache.new_page()` and can return
  `CacheFull`/`SpillwayFull`. Those are operational (`error.rs:161-174`), so the `?` propagates without
  poisoning and leaves `active_txn = true`. `delete_inner` is the mirror: the tombstone root is assigned
  before `membership_index.remove`.
  WHY: The in-code invariant is "Both must agree at all times" (`:1232`). On the failure window a
  `commit()` — the documented recovery from `CacheFull` (`lib.rs` Options docs; `error.rs:49-60`) — makes
  the divergence durable: after allocate, `tag(h)` returns the tag but `handles_with_tag(tag)` omits `h`;
  after delete, the tombstoned handle lingers in the index, and a later `delete_with_tag` feeds that stale
  handle to `delete_inner`, whose `lookup` hits the tombstone and returns the **fatal** `CorruptPage`
  (`:1582`) — escalating an operational state into a poison. Reachability is narrow (requires cache+spillway
  exhaustion at the exact mid-call point; with the default 8 GiB spillway, `SpillwayFull` is hard to hit,
  but `spillway_max_bytes = 0` makes `CacheFull` reachable).
  FIX: Stage both new roots and assign them only after both COWs succeed; or treat allocation exhaustion
  encountered after the first sub-mutation of a compound tag operation as fatal so the manager poisons
  rather than offering a committable diverged state.

- **BUG (corrupt-input) — `src/membership_index.rs:22-24, 63-77, 85-97, 442-444`: corrupt radix depth →
  out-of-bounds panic instead of `CorruptPage`.**
  WHAT: `unpack_inner` takes the top 6 bits of an outer-leaf value as the inner-tree `depth` with no
  validation. `RadixU64::find_leaf` then computes `span_at_level`/`capacity` by multiplying `SLOTS_PER_PAGE`
  (1021) `depth` times with plain `*=` (overflow panics in debug, wraps in release), and `read_slot` does an
  unchecked `buf[off..off+8]` where `off = 16 + child_idx * 8`. A wrapped span makes `child_idx` exceed the
  page, so the slice is out of bounds.
  WHY: A page whose XXH3 still verifies but whose bytes are structurally corrupt (the checksum is the only
  load-time trust boundary — `page_cache` does not validate page-type/slot contents) drives every
  `MembershipIndex::insert/remove/lookup/handles_for_tag` into this descent → library-reachable panic. The
  engine elsewhere deliberately converts such sites to typed `CorruptPage` (I14/I45/I49), so the radix
  modules are the inconsistent ones. `handle_table.rs::capacity()` (`:426-432`) has the same unchecked
  multiply at depth ≥ 6.
  FIX: Validate `depth` after `unpack_inner` (≤ 6 for u64 keys) and reject with `CorruptPage`; make
  `capacity()`/`span_at_level()` use `saturating_mul`; have `read_slot` bounds-check `index < SLOTS_PER_PAGE`
  and surface `CorruptPage`.

- **SMELL — `src/membership_index.rs:405-424` and `src/handle_table.rs:389-409`: `recover_depth` has no
  depth cap and no cycle guard.**
  WHAT: Both walk the leftmost spine following child-0 while the page type is interior, with no bound and
  no visited set.
  WHY: A corrupt-but-checksummed interior page whose child-0 points to itself (or forms a cycle) loops
  forever — an open-time / rollback hang on corrupt input. It is an accepted engine-wide posture (the two
  implementations match), but combined with the depth-panic above the membership index has two corrupt-input
  vectors into the same descent.
  FIX: Cap the loop at the u64 radix maximum (≤ 6) and return `CorruptPage` if exceeded.

- **NIT — `src/transaction.rs:889`: `self.txn_counter += 1` is an unchecked `u64` increment in
  `commit_inner`.** Practically unreachable (2^64 commits), but a wrapped counter would corrupt
  `Superblock::select`'s "highest counter wins" ordering, and a debug-build overflow panics mid-protocol
  after the pre-drain flush already cleared dirty flags. Use `checked_add` → fatal, matching the
  `saturating_add` discipline already applied in `delete_with_tag_inner`.

### Error handling

- **DESIGN — `src/transaction.rs:1651-1687`: `delete_with_tag` loses the partial-deletion list on a
  mid-pass error.** On `delete_inner(h)?` failing, the `?` discards the already-built `deleted` set; the
  caller gets only `Err`, never the `TagDropProgress` naming which handles were dropped this pass. The
  chunks *are* tombstoned in `current_roots` (consistent with `delete_many`'s posture), but for a bounded,
  resumable relation-drop the lost progress list means the caller can't reconcile. Combined with the
  divergence bug above, a non-fatal mid-pass failure can leave a committable diverged state with no report.
  FIX: Return the partial `TagDropProgress` alongside the error (a structured error carrying `deleted`), or
  document explicitly that the deleted-this-pass set is unrecoverable on error and rollback is mandatory.

### API design

- **DESIGN — `python/src/errors.rs:98, 241`: `IoError` does not subclass Python `OSError`.** The binding
  manually `setattr`s `errno`/`kind` onto a plain-`Exception` subclass to mimic `OSError`'s interface, so
  idiomatic `except OSError as e: if e.errno == errno.ENOSPC` never catches a Chisel disk-full error. The
  I42 work plumbed `raw_os_error()` through but stopped short of the inheritance that makes it useful.
  FIX: Derive `IoError` from `PyOSError` (needs reconciling with the `FatalError` parent — multiple
  inheritance set up Python-side, or a documented decision to keep them separate), or document why
  `except OSError` doesn't work.

- **DESIGN — `src/spillway.rs:128-130, 159-160`: spillway capacity is accounted against a monotonic
  high-water mark, not the live resident set.** `logical_bytes()` and the `SpillwayFull` check use
  `next_slot_index * PAGE_SIZE`; `forget`/`forget_above` never decrement it. A long transaction that reads a
  spilled page back and respills it under pressure consumes a fresh slot each cycle, so `SpillwayFull` can
  trip while live occupancy is far below `spillway_max_bytes`, and `Stats::spillway_logical_bytes`
  over-reports (the documented PR-U quirk, here with the cap-unpredictability consequence). Operational, not
  corruption.
  FIX: Either document the cap as "cumulative spill volume per transaction, not live occupancy," or compute
  the `SpillwayFull` decision and the reporting accessor from `slots.len() * PAGE_SIZE`.

### Concurrency

- **SMELL — `python/src/db.rs:227, 244, 614, 624`: `self.inner.lock().unwrap()` bricks the handle if the
  `Mutex` is ever poisoned.** A `std::sync::Mutex` poisons if any thread panics while holding the guard;
  thereafter every call (including `close()` and `is_poisoned`) panics into a `PanicException`. The engine is
  designed not to panic (it returns `ChiselError::Poisoned`), so this is not reachable today, but a single
  engine-side `debug_assert!` in a debug build, or any future engine panic, converts a *recoverable*
  poisoned-engine state into an *unrecoverable* poisoned-Mutex one. The module's I21 comment reasons about
  lock reentrancy but not poisoning.
  FIX: `.lock().unwrap_or_else(|e| e.into_inner())` (or `parking_lot::Mutex`, which doesn't poison) so a stray
  panic degrades to the normal poisoned-engine path; at minimum make `close()`/`is_poisoned` poison-tolerant.

- **DESIGN — `tests/basic_ops.rs:77`: handle-0 / `next_handle` durability across reopen is untested.**

### Docs vs reality

- **BUG — `src/freemap.rs:14-17`: comment claims handle-table page frees feed the freemap; they don't.**
  "Overflow and handle-table pages still extend directly … but their frees do feed the freemap on commit."
  Overflow frees do (`transaction.rs:1475`); handle-table COW supersessions never reach `txn_freed_pages`
  (finding 1). The comment asserts the exact reclamation that is missing. Fix the comment (and the leak).

- **BUG — `ARCHITECTURE.md:397`: `Deleted = 0x03` contradicts the code's canonical `0x00`.**
  `HandleFlags::to_u8` encodes `Deleted => 0x00` (`handle_table.rs:101`), and the load-bearing comment at
  `:103-107` explains zeroed pages must decode as all-tombstone. `from_u8` maps anything not `0x01`/`0x02`
  to `Deleted`, so `0x03` decodes correctly *by accident*, but the canonical on-disk byte is `0x00`. For a
  "sacred within a major version" format, correct the spec to `Deleted = 0x00`.

- **SMELL — `README.md:280` (operational error list) omits `TransactionInProgress`.** `error.rs:75` defines
  it (raised by the `set_*` config mutators mid-transaction) and `lib.rs:671/681/690` document it on those
  methods, but the README's enumerated operational tier doesn't list it. Add it.

- **SMELL — `python/README.md:350, 359`: `ClosedError` and `IoError` docs drift from the binding.**
  The `ClosedError` row says it fires only "through a `Transaction`/`Savepoint`," but the binding raises it
  for *any* post-close call including a bare `db.begin()`/`db.read()` (and `test_close_then_call_raises_closed`
  asserts exactly that). The `IoError` row omits the `.errno`/`.kind` attributes that the `.pyi` stub and
  I42 expose — defeating the feature for README-only readers. Reword both.

- **SMELL — `src/data_page.rs:48, 90, 349-352`: `compact()` names the reserved 8..16 bytes
  "txn_counter," contradicting the module header and `ARCHITECTURE.md:298`** (both call it the I31 reserved,
  universally-zero common-header region). The save/restore is a defensive no-op today, but the invented
  field name could lead a maintainer to actually stash a counter there, colliding with a future common-header
  field. Rename to "reserved common-header bytes."

### Idiomaticity

- **SMELL — `src/handle_table.rs:445-460, 480-491`: `grow()` allocates a page that `insert_recursive`
  immediately re-COWs, orphaning one fresh page per growth level.** `insert` calls `grow` (new interior
  root pointing at the old root at child 0), then `insert_recursive` on that root, whose first act is to COW
  it again. The `grow` page is referenced by nothing. Rare (grows only), but pure waste that also compounds
  the leak (finding 1). Either build the grown root already pointing at the new child, or mutate the
  just-created (uncommitted, unshared) interior page in place.

- **NIT — `src/page_cache.rs:778-793, 473-485, 912-930`: three hand-copied clean-victim eviction loops with
  subtly divergent short-circuits.** `maybe_evict` Phase A, `set_cache_max_bytes`, and `flush` Phase 1b
  duplicate the victim-selection walk; Phase 1b omits the `dirty_count` early-out. Correct today, but a fix
  to the eviction predicate must be made in three places. Extract one `evict_clean_to_cap` helper.

- **SMELL — `src/transaction.rs:1081`: `rollback_to_inner` restores roots/live_slots/cursor but not
  `current_freemap`.** The safety argument is "freemap reuse is disabled while savepoints active," but a txn
  can consume a freemap bit via `allocate_data_page` *before* its first savepoint; `rollback_to` then leaves
  that bit "used." The effect is conservative (a leaked bit reclaimed on next open, never a double-alloc),
  so not a correctness bug, but it's an undocumented gap in the "savepoints snapshot everything mutable"
  story. Either snapshot `current_freemap` per savepoint, or add a one-line note that it's intentionally
  excluded and why the residual is harmless.
