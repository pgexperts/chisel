## Executive summary

1. **`ChiselError::is_fatal()` is fail-open: any future variant not in its `matches!` list is silently
   classified *operational* and will NOT poison the manager** (`src/error.rs:168-181`). For a durability-first
   engine, the one function that decides "poison vs. keep serving over questionable on-disk state" defaults to
   "keep serving." The in-code INVARIANT comment admits it's "a durability hole, not a compile error." (DESIGN)
2. **The PyO3 binding (1,300+ lines of Rust) is never clippy-linted in CI** (`.github/workflows/ci.yml:40`):
   the gating `cargo clippy -- -D warnings` honors `default-members = [".", "bench"]`, which excludes
   `chisel-py`; the python job runs only `maturin develop` + `pytest`. Clippy regressions in `python/src/*`
   ship silently. (BUG)
3. **The radix addressing math — the core of both the stable-handle table and the tag index — has no property
   tests, and the one multi-level test never reaches depth ≥2** (`src/handle_table.rs:1313`,
   `src/membership_index.rs`). `span_at_level`/`find_leaf`'s multi-digit decomposition is the engine's most
   off-by-one-prone code and is exercised only at depth 0–1. (DESIGN)
4. **The ADR and ARCHITECTURE.md describe an unimplemented mechanism as live**: ADR-7 and `ARCHITECTURE.md:580`
   claim "reads dispatch on the per-page version byte" / "the page-cache load path validates the per-page
   version on every miss," but no code reads that byte (`PageCache::load_page` validates only the XXH3
   checksum). Compounded by `ARCHITECTURE.md:246` citing a deleted function `page::page_format_version()` and
   `:108/:471` documenting the deleted `allocate_near`. (BUG — docs vs reality, from the #46 dead-code sweep)
5. **`current_live_slots` / `committed_live_slots` / `Savepoint.live_slots` use std `HashMap` (SipHash)**
   (`src/transaction.rs:144`, fields at ~144/216) on the per-op slot-accounting path. The I77 FxHashMap pass
   converted the page cache and LRU but missed these maps — the same free win, left on the table. (DESIGN/perf)

## Countercase on the single most important finding (per request)

**Finding #1 — `is_fatal()` fail-open default.** Arguing against fixing it:

- It is **latent, not a present bug**. Every one of the 24 current variants is correctly classified; the gap
  only opens if a *future* maintainer adds a fatal variant and forgets to list it. The enum already groups
  variants in labeled "Fatal"/"Operational" blocks and the `is_fatal` body carries a loud INVARIANT comment,
  so the omission is visible at the point of the change and code-review-catchable. These variants have no
  external constructor — they arise only from in-tree engine code, never from untrusted runtime input.
- The obvious fix — **invert the default to `_ => true` (unknown ⇒ fatal)** — has its own real failure mode.
  A future *operational* variant (another precondition error like `NoActiveTransaction`) added without
  updating `is_fatal` would then **poison the manager on a cheap, recoverable error**, forcing a long-running
  service into a drop-and-reopen it didn't need. Over-poisoning degrades availability exactly as silently as
  under-poisoning degrades durability; flipping the default just moves the latent bug, it doesn't remove it.
- So as a *default-flip*, it's arguably not worth it: you trade one latent misclassification class for another.

**Honest net recommendation:** Fix it — but not by flipping the default. Add the cheap belt-and-suspenders the
comment is asking for: an exhaustiveness test that constructs **every** `ChiselError` variant and asserts
`is_fatal()` equals the value the enum's documented Fatal/Operational block prescribes. That converts the
prose invariant into the compile-time-ish signal the `#[non_exhaustive]` enum can't provide, catches *both*
directions of misclassification, and changes zero runtime behavior. ~30 lines, no risk. Worth doing; the
default-flip is not.

## Findings by category

### Correctness

- **DESIGN — `src/page_cache.rs:625-654` (`truncate`): `self.dirty_count -= 1` per removed dirty entry is
  unguarded, unlike every sibling decrement.** `discard`, `maybe_evict` Phase B, and `set_cache_max_bytes` were
  all guarded against an `entries`/`dirty_count` desync (the explicit comment at `:986-994` justifies exactly
  this); `truncate` is the outlier. On any desync it underflows (debug panic / release wrap to `usize::MAX`),
  after which `maybe_evict`'s `dirty_count == entries.len()` short-circuit never fires and the cache silently
  stops enforcing its cap. Fix: recompute `dirty_count` from surviving entries after the loop, or saturate —
  consolidate all four sites behind one helper.
- **DESIGN — `src/transaction.rs:2576` (`insert_into_data_page`): `.expect("value fits in empty page")` is a
  library-reachable panic if the inline-size constants ever drift.** Correct today (`MAX_INLINE_VALUE = 8162`
  exactly equals `CHECKSUM_OFFSET - DATA_PAGE_HEADER_SIZE - SLOT_ENTRY_SIZE`), but `MAX_INLINE_VALUE`
  (`transaction.rs:66`) is a hand-maintained literal with only a prose "keep in sync" note; if any of the three
  constants is edited independently, `DataPage::insert` returns `None` on the "fits" path and a plain
  `allocate(value)` of the wrong-sized value panics the process. Fix: `const _: () = assert!(MAX_INLINE_VALUE ==
  CHECKSUM_OFFSET - DATA_PAGE_HEADER_SIZE - SLOT_ENTRY_SIZE);`, or map the `None` to a typed error.
- **SMELL — `src/membership_index.rs:603` + `:41-49`: fresh inner-tree roots bypass the freemap-aware
  allocator, undercutting the module's own "bounded steady-state page count" claim.** `MembershipIndex::insert`
  threads the freemap-aware `alloc` closure into `inner.insert`, but a tag's first-ever `create_root` →
  `init_page` → `cache.new_page()` always extends (never reuses a freed page). Not a correctness bug (the id is
  past the watermark; rollback's `truncate` and commit's freemap merge both handle it), but a churn workload
  that repeatedly empties and re-creates a tag's inner tree extends the file once per re-create. Fix: plumb the
  `alloc` closure into `create_root`/`init_page`, or narrow the header comment.
- **NIT — `src/transaction.rs:889` (`commit_inner`): `self.txn_counter += 1` is an unchecked `u64` increment**
  (carried from the prior review). Practically unreachable, but a wrapped counter corrupts `Superblock::select`'s
  "highest counter wins"; a debug overflow panics mid-protocol after dirty flags were cleared. `checked_add` →
  fatal would match the `saturating_add` discipline used elsewhere.

### Ownership / borrowing

- **No finding.** The `RefCell<PageCache>` + `Cell` poison/counter discipline holds; every mutator takes a

### Error handling

- **DESIGN — `src/error.rs:168-181` — `is_fatal()` fail-open default.** (Executive #1; countercase above.) The
  `matches!`-based classifier returns `false` for any unlisted variant ⇒ operational ⇒ no poison. Fix: an
  exhaustiveness test constructing every variant (not a default flip).
- **DESIGN — `src/error.rs:282-286`: the blanket `From<io::Error>` makes every `?` on an I/O call produce a
  *fatal* `IoError` invisibly.** The comment (`:280-281`) concedes callers "must catch and remap" to classify
  e.g. `NotFound` as operational; nothing enforces it, so any future `?` on an io call silently poisons on a
  benign error. The `FileNotFound` operational variant exists precisely because the conversion is too coarse.
  Fix: drop the blanket `From` (force explicit classification at each I/O site), or have it inspect `ErrorKind`
  for the known-operational kinds.
- **DESIGN — `src/error.rs:106`: `CorruptSuperblock` folds three distinct causes** (bad checksum, bad magic,
  out-of-range `superblock_count`) into one nullary, *fatal*, unrecoverable variant; the comment admits
  operators "should look at the raw slot bytes." Throwing away which-slot-and-why on the engine's worst
  failure is an operability loss. Fix: a cause field (`enum SuperblockDefect { Checksum, Magic, BadCount(u32) }`)
  and/or the slot index.
- **DESIGN (unchanged from prior) — `src/lib.rs:553` / `transaction.rs:2041`: `delete_with_tag` discards its
  partial-deletion list on a mid-pass error.** The `?` drops the already-built `deleted` set; the caller gets
  `Err` with no `TagDropProgress`. State stays consistent, but a resumable relation-drop can't reconcile what
  it dropped. Fix: attach the partial progress to the error, or document that rollback is mandatory on error.

### Async

- **No finding.** No `async` anywhere; the synchronous single-writer contract is intact and deliberate.

### API design

- **DESIGN — `src/lib.rs` (handles raw `u64`, tags raw `u32` across the whole surface).** `allocate -> u64`;
  `read`/`update`/`delete`/`tag`/`handle_live_page_id` take `u64`; `delete_tagged(handle, tag)` takes two
  integers the compiler can't keep from being swapped. A crate that is `#[non_exhaustive]`-everything and
  careful about API stability leaves its most-used values primitive-obsessed. Fix: opaque `Handle(u64)` /
  `Tag(u32)` newtypes with `From`/`Into` — makes `delete_tagged` un-transposable and distinguishes
  `handles()` from `handles_with_tag()` return types.
- **DESIGN — `src/lib.rs:492,607`: `handles()` / `handles_with_tag()` return `Vec<u64>` (eager, O(live)) where
  the contract is three paragraphs of "identical Vec, order unspecified" prose.** The `file_size_bytes()`
  accessor (`:668`) was split out specifically to avoid `handles()`' full scan — evidence the eager Vec is a
  known cost. Fix: keep `Vec` but document why eager, or offer a streaming variant; the prose-as-type-contract
  is the deeper smell.
- **SMELL — `src/defrag.rs:111` / `src/membership_index.rs:538`: `DefragStats` and `TagDropProgress` are
  outcome-report structs but not `#[must_use]`.** `db.defrag(opts)?;` silently discards `pages_freed`;
  `delete_with_tag(...)?;` discards `complete` — the field the caller must loop on. The crate already added a
  custom `#[must_use]` to `close()`, so it values this. Fix: `#[must_use]` on both type definitions.
- **SMELL — `src/defrag.rs:64-70`: `DefragOptions::max_pages` counts *values relocated*, not pages** ("DESPITE
  THE NAME…"). Preserving a misleading public field/setter name "for stability" on a pre-1.0,
  `#[non_exhaustive]`, no-production-users crate is the wrong trade. Fix: rename to `max_values` now.
- **SMELL — `src/page_io.rs:330,594`: `page_count`/`file_page_count` keep `&mut self` "for API stability" on a
  pure `Cell` read,** forcing `borrow_mut()` on `&self` read paths. Drop the `&mut` now (the comment already
  concedes a future patch can); the ripple is small.
- **NIT — public fallible methods broadly lack `# Errors` rustdoc** (`savepoint`/`rollback_to`/`release`/
  `set_root_name`/`get_root_name`, and most `TransactionManager` mutators), and several omit `# Panics` where
  they assert (`transaction.rs:307` superblock-count range, `membership_index.rs:167` debug-only non-zero
  precondition). For a published crate this is `missing_errors_doc`/`missing_panics_doc` surface. Fix: a shared
  "Errors & poisoning" doc convention plus targeted sections.

### Type system usage

- **DESIGN — `src/transaction.rs:1563-1602`: three different deleted-handle semantics for the same "look up a
  live handle."** `read()` and `client_byte()` reject a tombstone with `InvalidHandle`; `tag()` reads through
  it; `delete_tagged()` (`:2014`) reads `.tag` off the looked-up entry with no Deleted guard. The "a handle is
  live" invariant lives in scattered per-method guards. Fix: one `lookup_live(handle) -> Result<HandleEntry>`
  applying the Deleted⇒`InvalidHandle` rule once, used by all four.
- **SMELL — `src/lib.rs` tag surface: `0` is overloaded as the "untagged"/"unset" sentinel** for both tag
  (`u32`) and client byte (`u8`), threaded through the whole membership layer. `allocate_tagged(value, tag: u32)`
  can be called with the sentinel by mistake. Fix: `Option<NonZeroU32>` at the tag API boundary — then "no tag"
  is expressed in the type and "membership index not updated for tag 0" becomes "there is no tag."

### Performance

- **DESIGN — `src/transaction.rs:144` + the manager's `current_live_slots`/`committed_live_slots` fields use
  std `HashMap` (SipHash) on the per-op path.** Probed/updated on every insert/update/delete
  (`insert_into_data_page:2555/2591`, `release_data_slot:2463`). Keys are trusted local `u64` page ids —
  identical threat model to the page-cache/LRU maps that I77 already moved to `FxHashMap` with an explicit "no
  DoS surface, SipHash is pure cost" rationale. These were missed by that pass. Fix: `rustc_hash::FxHashMap`
  for these (and `Savepoint.live_slots`); zero-risk, same free win.
- **SMELL — `src/transaction.rs:1694`: `read()` copies via `data.to_vec()` on every inline read.** `DataPage::read`
  already returns a zero-copy `&[u8]`; the copy is forced by the public `read(&self) -> Result<Vec<u8>>`
  signature (can't lend a borrow tied to the `RefCell` `borrow_mut()`). Not free to remove (API + borrow
  lifetime). Fix: an optional `read_into(&mut Vec)` for hot callers; leave `read` as-is. (Unchanged F2.)
- **Clean (verified, not assumed):** LRU is O(1) intrusive-list-over-FxHashMap; page cache reuses
  `dirty_scratch` and short-circuits the eviction scan on `dirty_count`; radix descent is allocation-free per
  op; XXH3 is re-stamped once per touched page (not per value — the deferred I78 per-value concern does not
  appear on these paths); `Box::new([0u8; PAGE_SIZE])` allocations are genuinely-new pages only.

### Idiomaticity

- **SMELL — the COW page copy bounces through a named 8 KB stack array** (`handle_table.rs:330-333`,

### Python binding (PyO3) — subsystem notes

- **DESIGN — `python/src/db.rs:2-29`: the file-header doc still describes the engine as `RefCell<Option<Chisel>>`
  and argues "why RefCell (and not Mutex)" — the actual field (`:76`) is `Mutex<Option<Chisel>>` (I75).** The
  struct comment 30 lines below correctly documents the Mutex migration and contradicts the header above it; a
  first-time reader gets the wrong concurrency model and the wrong I21 failure mode (RefCell *panics* on
  re-entry; the Mutex *deadlocks*). `transaction.rs:44` has the same stale claim. Fix: rewrite both headers.
- **DESIGN — `python/src/errors.rs:326`: the `_` catchall routes any future variant to the abstract
  `ChiselError` base, bypassing the Operational/Fatal split.** A new *fatal* engine variant would surface in
  Python as a bare `ChiselError`, so `except chisel.FatalError:` poison-recovery handlers silently miss it —
  breaking the documented FatalError contract (`errors.rs:5-7`). This is the same fail-open class as engine
  finding #1, on the binding side. The header (`:11-13`) also still claims the match is exhaustive with "no
  silent fallback," which `#[non_exhaustive]` (I36) made false. Fix: branch the catchall through the
  Operational/Fatal base; correct the header.
- **SMELL — the typed-exception contract is largely unverified.** Routing is currently correct, but
  `SavepointNotFoundError`, `DuplicateSavepointError`, `CacheFullError`, `SpillwayFullError`,
  `RootNameTableFullError`, `InvalidRootNameError` are never raised in any test, and `test_operational_hierarchy`
  omits `TagMismatch`/`SpillwayFull`/`TransactionInProgress`. A swapped `to_py_err` arm ships green.
  `test_threading.py` joins before re-touching, so the Mutex deadlock/poison path (the whole reason for the
  Mutex-over-RefCell decision) is unexercised. Fix: parametrized "trigger each variant, assert the concrete
  class" test; a two-thread contention test.
